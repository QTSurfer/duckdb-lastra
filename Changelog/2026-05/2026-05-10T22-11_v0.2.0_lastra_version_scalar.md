# 0.2.0 — `lastra_version()` scalar function

**Date**: 2026-05-10

## What

New SQL scalar function `lastra_version()` returning the compiled extension
version as `VARCHAR`. Clients (analytics-runtime, ad-hoc DuckDB sessions,
notebooks) can validate they loaded the expected build before running queries
that depend on a recent codec fix or feature.

```sql
SELECT lastra_version();
-- 0.2.0
```

## Why

The extension version had drifted: `src/lastra_extension.cpp::Version()`
returned `"0.1.0"` while the community-extensions descriptor advertised
`0.1.1`. There was no way for a client to programmatically check what build
was actually loaded inside a DuckDB session. As we add codec fixes (e.g. the
ALP per-vector iteration regression already fixed) and roll out via
community-extensions, downstream code needs to detect mismatches between
locally cached binaries and the version it expects.

## How

- Single source of truth: `LASTRA_EXTENSION_VERSION` macro in
  `src/include/lastra_extension.hpp`.
- `LastraExtension::Version() const` now returns that macro.
- New `LastraVersionScalar` registered as `ScalarFunction("lastra_version",
  {}, VARCHAR, ...)` in `LoadInternal`.
- Bump to `0.2.0` (MINOR — new public SQL surface, fully additive).
- Community-extensions descriptor bumped to `0.2.0` to match. The previous
  `0.1.1` entry was never submitted to `duckdb/community-extensions`, so no
  external coordination is needed.

## Tests

`test/sql/lastra.test` now starts with:

```
query I
SELECT lastra_version();
----
0.2.0
```

The hardcoded literal is intentional — if someone bumps the macro without
updating the test (or vice versa), CI catches it.

## Compatibility

- Read-side: zero changes. Existing `.lastra` files keep working.
- Loader: any client that doesn't call `lastra_version()` is unaffected.
- Re-submission to `duckdb/community-extensions` required to pick up the new
  binary in the public CDN.
